# 守望谷 v0.3｜世界时间、四季与天气框架

> 状态：设计规格，尚未实现。主旨：让山谷能够“日复一日、季复一季、年复一年”地生活，不再几天内走完一生。
> 依赖：`src/simulation/world.ts`（状态唯一事实来源）；`src/main.ts`（UI/帧循环）；`src/graphics/village.ts`（视觉）。

## 1. v0.2 现状与问题定位

当前 `DAY_MINUTES=1440`、`MINUTES_PER_REAL_SECOND=6`，即 **1× 下 4 分钟便过去 1 个游戏日**。阿青事件里 `training/departed/rumor/returned/legacy` 在选择后约 120/1500/3000/4500/5600 游戏分钟触发，最终结局不到 4 个游戏日。这就是“几天走完剧情”的主要原因，**不是仅仅把流年倍率调低就能解决**。

当前昼夜、故事年龄与建造发展共同依赖 `minutes`，缺少季节、天气、建筑周期、人物年龄、阶段条件；同样缺乏跨年事件的语义边界。

## 2. 玩家体验承诺

- **3 分钟**：看到日常作息、草木摇动、远客进出、天气细节；即使没有大事，也值得观察。
- **10–20 分钟**：至少看到一项可追溯的生活反馈（修篱笆、晒药、添置酒坛、村口出现脚印），但**不保证**大侠归乡。
- **跨季**：种植、酒馆访客、服饰、景观、修缮计划因季节改变。
- **跨年**：人物年龄、外游归乡、门派萌芽、房屋更迭由“流年条件 + 事件前提”决定。
- 玩家不在时世界仍能推进；回归有摘要，绝不以无人值守的破产/灭村惩罚玩家。

## 3. 三层日历：同一权威时钟，三种更新频率

不要维持三个会相互漂移的独立时间变量。**单一权威模拟时间 `world.minutes`，日历派生；每日/每季/每年由事件边界驱动。**

| 层级 | 数据粒度 | 主导内容 | 不应承担 |
|---|---|---|---|
| 日常 | 分钟、小时、日 | 起居、行动、灯火、一次交互、施工动画 | 人物长大数岁 |
| 时节 | 每 12 游戏日为一季 | 春夏秋冬、农产、天气权重、材料供应、年度修缮 | 突然解锁完整人生 |
| 流年 | 四季共 48 游戏日为一年 | 年龄、长期声望、房屋寿命、游历与传承 | 反复刷同一事件 |

**供首轮平衡测试的建议值，未定版：**
- 1×：**8 分钟现实时间 / 游戏日**，即 `3` 游戏分钟/现实秒。
- 4×、12×：用于短时间观察，保留在页面中的玩法位置。
- `流年`：从现有 **48× 持续倍率** 改为 **“推进到下一个季节边界”** 的明确操作；播放摘要与局部可视变化。一次操作最多跨一季，避免无意识跳完故事。
- 春夏秋冬各 12 日，一年 48 日；1× 全年约 6.4 现实小时，这是**初始节奏假设**，后续依据实际玩家观察时长调整。

**重要：** 不能把“年级事件”完全锁在流年按钮后。正常时钟最终也会跨年；流年只是主动加速观察，而不是第二套剧情时钟。

## 4. 时间边界与批处理合同

建议纯函数接口（尚未实装）：

```ts
type Season = 'spring'|'summer'|'autumn'|'winter';
type Weather = 'clear'|'cloudy'|'rain'|'fog'|'wind'|'snow';
interface CalendarView { year:number; dayOfYear:number; season:Season; dayOfSeason:number; hour:number; minute:number; }
interface WorldAdvanceSummary {
  crossedDays:number; crossedSeasons:number; crossedYears:number;
  journalIds:number[]; visualChanges:string[]; pendingChoices:string[];
}
getCalendar(state): CalendarView
advanceSimulatedMinutes(state, delta): WorldAdvanceSummary
advanceToNextSeason(state): WorldAdvanceSummary
```

- 采用“跨过哪些边界，就处理哪些边界”的事件调度；正常步进、大步长快进与离线恢复必须收敛到相同状态。
- 状态与可视事件以 **唯一 ID** 去重；不要每跨一日就写一条千篇一律的编年史。普通生活可聚合为“本季小记”。
- 旅人、建造、人物成长、修缮进度由各自条件推进，不应依赖浏览器每帧渲染。
- 一段故事触发至少要求：`timePrerequisite` + `worldPrerequisites` + `characterPrerequisites`；年龄和“已建立师徒关系”均是显式事实。

## 5. 人物生命周期与剧情节奏

- `birthYear / age / lifeStage` 独立于“角色显示在地图上”。少年、青年、壮年、老年只在跨年/特定节点检查。
- 阿青样例**最短时间线**：第一年可遇侠客与修习；第二年之后可出游；第四年之后才有归乡机会。具体回乡仍看经历、师承、社会关系，而不是到点瞬移。
- 每年应有“至少一种非传奇但可见的变化”（树长大、老屋翻修、添新居、摊位迁移），世界不能因主线完成而静止。
- 建议把 v0.2 完结故事保留为历史或迁移前序，而不是在加载旧存档时反复播放全段。

## 6. 天气：从模拟确定状态，到分层视觉

气候由 `season + elevation/region + seed + calendarDate` 决定，避免用 `Math.random()` 在渲染帧里抽取天气。

| 季节 | 主色/植被 | 天气权重（方向） | 居民/村庄反馈 |
|---|---|---|---|
| 春 | 嫩竹、湿润草地 | 小雨、薄雾更常见 | 插秧、药圃返青、修路 |
| 夏 | 浓绿、暖日照 | 晴、阵雨、风 | 酒肆晚间活跃、晾晒 |
| 秋 | 黄绿、丰收、落叶 | 晴、干风、晨雾 | 收获、存粮、翻修 |
| 冬 | 枯枝、冷空气、可选薄雪 | 霜、雾、雪（非每日） | 炉火、厚衣、避寒修屋 |

天气不是全局换色：
1. **环境层**：日照色温、雾浓度、天空亮度、地面湿度。
2. **场景层**：檐滴、积水/浅雪、竹影摆动、屋顶覆盖与河岸细节。
3. **行为层**：行人快步、撑伞/蓑衣、坐在炉边、改去室内。
4. **世界层**：天气影响耕作/游客/修缮速度，但低频、温和，不致离线毁家。

**首个实现批次：** 春夏秋冬静态对照 + 晴/雨/雾三种天气；雪、风与积雪体积留下一批。不允许仅叠一层屏幕滤镜假装季节成立。

## 7. 放置/离线/存档

- 离线模拟必须**有限、可解释、可复现**，建议第一版每次恢复最多推进 **4 游戏日** 并显示“离线结算上限”，后续再依据实际玩法调优；不要沿用 `120s` 的实现而不重新评估。
- 重大危险不在离线时无预警地自动摧毁建筑；可转成“待回应危机/已采取保守措施”。
- `version:3` + 新 `STORAGE_KEY` 或显式迁移方案；**不覆盖 v0.1/v0.2 原存档**，提供备份/新开档入口。
- 可重复尝试不同分支：至少两个本地存档槽位 + 新游戏确认 + 导出/导入 JSON 的规划接口。
- 不允许写死全新 v0.3 开局使玩家被迫丢失既有江湖故事；设计可解释的迁移或保留旧档只读。

## 8. 验收、测试与非目标

- 纯模拟测试：正常步进 vs 一季快进 vs 离线恢复的最终状态和事件 ID 一致；重复恢复不重放事件。
- 校验 4 个季节边界、年末、闰日（本游戏无闰日）、天气与固定种子可重现。
- 1× 玩家游玩 15 分钟不得触发“少年从初见到功成归乡”。
- 流年推进有摘要；没有回应的机缘可自动演化，但关键危险必须预警。
- 浏览器截图矩阵：四季日景 + 春雨 + 秋雾 + 冬夜；检查场景可读性与性能。
- 非目标：真实天文学、实时云端模拟、大模型生成天气、复杂日历节气表。

## 9. 开发顺序

1. 测试驱动抽出 `calendar.ts`、`weather.ts`，保留单一模拟时钟。
2. 把现有基于 120–5600 分钟的故事迁移成跨年阶段条件；配套存档版本化。
3. 接入日历 UI、流年预览与离线摘要。
4. 先完成四季材质/环境状态及晴雨雾，再增加行为与生产变化。
5. 对照截图、运行性能与多倍率/离线回归后才扩展更多故事。
