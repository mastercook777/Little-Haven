## 0. 一句话定位与决策摘要

**玩家不是建造师，而是守谷人；村民因真实的需要在荒谷落脚、生活、经营、修路与建屋。玩家偶尔影响优先级，村庄则用自己的时间把选择变成看得见的历史。**

v0.4 不再把“已经造好的酒馆村庄”当作必然开局，而是新增 **「开荒模式」**：初始只有真实山谷、溪流、天然小径、三名居民、一处临时营火及随身物资。第一个棚子、第一条村路、第一处茶棚，以及后来的酒肆，都必须由同一个需求—选址—备料—施工—使用循环产生。

**决策（本版确定）：**
1. v0.3 现有完成村庄保留为 **「旧谷 / 经典观察模式」**，不动用户旧存档，不把旧世界直接清空。新模式独立开新档。
2. 开荒模式默认观赏优先、村民自治；玩家做的是季节性发展引导和重要机缘选择，不直接逐块手摆所有建筑。
3. **从零开始不是隐藏预制房屋再按日显示**：所有永久房屋、道路和产业地块，均由条件触发并经统一空间规则创建。
4. 首版地貌可沿用现有明亮、正交视角的浮岛、河床和植被；建筑初始占地不能复用 v0.3 已占满的 `BASE_PARCELS`。
5. “有生活”优先于“高速涨数值”。发展慢可以，停滞必须有原因、有村民应对；安静的小村庄也能是成功结局。
6. **先做开荒最小可玩切片（A），再做动态生活循环（B），最后迁入既有江湖事件（C）**。只有通过真实浏览器视觉验收才宣布相应阶段完成。

## 1. 为什么要重构开局，而不是继续扩建原村庄？

v0.3 的成就值得保留：单一世界时间、四季/晴雨雾、可观察角色生活、两种阿青选择、守望录、双存档、河槽地形、需求触发民居和 OBB/SAT 地块碰撞。但现有初始酒馆、五间民居、练武坪、桥及发展分区多由静态场景和保留地块预先摆好。三条路线仍有大量预制地标。因此：

- 玩家看见的通常是 **一座已完整的村庄升级**，不是家园从无到有；
- 建筑扩建被旧布局挤住：能延后穿模，却无法解释“村庄为什么一开始就这么密”；
- 村民虽走动，但房屋和工作常被固定角色路线锁定；社会关系不是建筑生产的原因；
- 玩家一季一季推进，缺少“这个棚子因为谁的需求才出现”的空间因果。

v0.4 的改法是 **用同一套世界数据生成初始聚落和后续增量**；老模式的现成资产只作为后期可建的建筑原型，不再自动加载为开荒地图。

### 1.1 明确不做

- 不做纯手动城市编辑器、科技树点点点、每日收税/点资源、挖矿刷数值或多人 MMO。
- 不要求外部大模型、联网服务器、付费美术 API；模拟必须本地可运行、可离线保存、可复现。
- 不以“随机散落几间新屋”冒充自主生长：随机只参与候选比较，**动机必须来自居民和环境**。
- 不在本轮开发真实战斗、门派政治、完整家庭遗传、每栋房屋室内、无限地图或自动建筑生成的高品质专业 GLB。

## 2. 两种模式与存档边界

| 维度 | 旧谷 · 经典观察（v0.3） | 开荒纪元 · 新谷（v0.4） |
| --- | --- | --- |
| 初始场景 | 酒肆、老屋、练武坪及已知村民 | 荒谷、水系、天然植被、小径、营火和三位开荒居民 |
| 核心过程 | 观察村庄变迁与阿青既有剧情 | 需求出现 → 商议 → 选址 → 劳作 → 新家园 → 新需求 |
| 建筑空间 | 大量历史坐标 + 后期规划 | **所有永久结构** 进入统一建筑注册表和规划器 |
| 玩家输入 | 剧情选择、机缘、发展方向 | 发展意向、关键取舍、可选的建议位置区域与机缘 |
| 存档 | 保持原 v3 双槽，不做破坏性改动 | 独立 v4 开荒双槽、独立 JSON 导入导出 |

进入游戏时明确显示 **「继续旧谷」** 和 **「开始开荒」**；新模式不自动删除旧模式，旧模式保存的世界也不被强行迁移成“空山谷”。

**兼容协议：** v3 `little-haven-living-v03-slot-1/2` 原样保留；新 v4 开荒使用独立前缀（建议 `little-haven-pioneer-v04-slot-1/2`），并记录 `mode:'pioneer'`、`schemaVersion:4`。v3 导入只进入旧谷；跨模式查看/导出可以，强制把已建老村回退为开荒数据**不支持**。所有 reset 只操作当前模式当前槽。旧谷现有功能应继续运行。

## 3. 开局场景：真正的“第一处烟火”

### 3.1 初始世界（P0 最小可玩基线）

- 一块有可站立高地、溪流、河岸、竹林、林缘和天然山口的山谷；保留旧版微缩浮岛、天气和正交镜头的可读性。
- **永久建筑数 = 0；公共道路建筑数 = 0；住户数 = 0**。
- 地面上可以有天然山径（足迹/地形痕迹，不是已修好的石路）；不可以有开局就存在的酒肆、桥市、练武坪、屋顶或任意看似已建成的永久设施。
- 一处临时营火属于 **营地物件**，不是“第一栋建筑”；随时可熄灭/迁移。三位角色拥有少量随身物资。
- 开局脚下的可用地块必须通过空间校验；若种子不适合营火扎营，选择另一片可建营地，不能穿入树木、河坡或崖边。
- 地形资源点可有有限个可视标识：枯枝、食用野物、取水处和耕作适宜地；不是可点击的金矿 UI。

### 3.2 初始三人及角色与命运

| 人物 | 开局身份 | 早期自主工作 | 对村庄发展的影响 |
| --- | --- | --- | --- |
| 梁伯 | 老练行山人／樵夫 | 检查安全地、采集枯木、搭支架 | 木料与避险知识，影响第一处避风棚与房址 |
| 陆娘 | 行路人／善照应的掌事者 | 生火、分粮、照看营地、迎接来者 | 营地生活效率、公共空间愿望；将来可经营茶棚／酒肆 |
| 阿禾 | 熟悉山野的采集者 | 采摘、试土、种植小块菜圃 | 粮食稳定度、可耕地判断与田园方向 |

这里的身份是**开局职能**，不是永久强制职业。居民遇到木料紧缺、天雨、寒冬、病弱或新工作机会，应能够适度更换任务。其他既有角色（沈叔、小七、苏婶、阿青等）在具备落脚、食物或社会条件后 **出现/迁入/成长**；江湖客只作为访客，不能算永久人口。

> **人物连续性原则：** 原有角色姓名、性格和关系应尽量保留；但开荒模式的年代与相遇顺序可以不同。阿青故事必须相对“真正到谷/开始习武”计时，不能沿用 v0.3 从世界第 1 天立刻启用所有人物的事件硬编码。

## 4. 玩家可感知的成长节奏（示例，不是硬编码日期）

时间沿用现有标准：**1 年 = 48 游戏日、4 季 × 12 日，1× 约 8 真实分钟/游戏日**；「流年」仍按一个季节推进。表格内的日数是 **设计目标窗口**，不是 `if (day===N) spawnHouse()`。

| 观察窗口 | 应能看见的变化 | 触发原则 | 守谷人 |
| --- | --- | --- | --- |
| 开始后 0–3 真实分钟 | 营火点起；有人勘地、拾柴、取水；篝火旁有聚集与分工 | 三位居民体温/饥饿/安定需求与营地物资 | 可建议营地优先取水或背风，但不介入也能开工 |
| 前 1–3 游戏日 | 简易遮雨棚／第一处可睡的屋顶从搭架到成形 | 遮蔽需求、木料、劳力、合规地块 | 可优先粮食或稳固住房 |
| 第一季 | 稳定食物来源、第一条人行踩踏路、炉火/储物设施；天气影响施工 | 有人反复走同一段路线、食物存量与坏天气 | 决定保护树木还是更快用木材 |
| 第一至第二年 | 1–3 个不同功能的常住点、简易耕地、小桥或渡口的需求 | 住户人数、取水跨河需求、外来者是否愿意留下 | 调整商旅／渡口／农圃的优先级 |
| 第二至第四年 | 条件满足时出现茶棚、酒肆、工坊；村庄公共区域被使用 | 商旅频率、食物结余、道路连通性、掌事者能力 | 是否支持接待商旅及公共建设 |
| 更久之后 | 新住户、修缮、屋舍老化、迁址、空房与生活方式改变 | 家庭/就业/地块/资源循环 | 决定扶持社区或顺其自然 |

开荒前 **10–15 真实分钟** 的 1× 实时观察，应至少经历 *营火→自发分工→一个实际施工对象→可使用的第一处遮蔽*；若受天气或资源制约而没建成，必须可见“为何未建成”和居民采取了什么补救行动。

「流年」可以快进，但任何跨日/跨季事件必须按同一时间顺序结算，保留施工中间态和可追溯记录；不能直接把美术从营火切换到满级酒馆。

## 5. 放置 + 轻度模拟经营：真正的内循环

### 5.1 需求比生产优先

每个居住群体至少有可计算需求：`food`（够吃多久）、`shelter`（夜间住所容量）、`warmth`（寒雨与冬天）、`waterAccess`（可获取的水）、`safety`（崖边/洪水/火堆）、`workAccess`（往返工作地点），后期再加入 `social` 与 `trade`。

**必须存在因果：** 下雨→棚子漏水→夜间不适/物资受损→产生修缮或新建需求→村民带木料施工→棚子变样；不是仅给 UI 加一个“舒适度 -5”。

为避免参数爆炸，P0 只把 **食物、遮蔽、木料/劳力、取水、安全** 做成权威计算；情绪、名望、买卖等可先做派生结果，不必同时模拟 10 种货币。

### 5.2 生产与资源

**主要物资：** 木料、食物、石料（石料可推迟到桥/石基解锁）。营火还需要燃料、季节影响保暖。**劳力是居民时间分配，不是可凭空累积的数字。**

- 村民每天有固定可用工作时段。采集、伐木、捕鱼、照料菜地、施工、休息互相竞争时间。
- 资源来自确有可见来源的 `ResourceSite`，并会减少、恢复或季节更替；不能从“每天自动 +3 木材”直接凭空生成。
- 消耗必须扣库；房屋施工若缺料暂停。每日食物应计入居民口粮，冬季可能少产多耗；不要出现资源负数。
- 资源可自动存于营地箱/粮仓；容量有限，天气会影响损耗，但不要求玩家手动领取或点击收菜。
- 提高采集强度可能损害附近林地/资源点；保护资源则早期建设较慢但后期更稳定。
- 食物与房屋是 **移民的前提条件**，不能将新居民直接加到 population 数值而没有身份、睡觉位置和工作安排。

### 5.3 一天的自治决策顺序（P0）

1. 读取世界日、季节、天气、居民/资源/建造中状态。
2. 先保证安全、口粮、取水、临时避寒；为次级工作计算剩余劳动力。
3. 识别最迫切的 `Need`，产出可说明原因的 `BuildIntent` 或 `WorkIntent`。
4. 对建造意图检查前置条件（角色、材料、用地、道路可达、容量等），由规划器选址并预留工地。
5. 居民在真实时间里去真实来源处取材和施工；建完投入使用，改变需求与人口迁移意愿。
6. 记录可见事件和因果链，更新工作点与道路。若失败，解释是缺料、天气、地块还是人手不足，改派任务而非卡死循环。

每个居民不能在同一分钟同时“伐木 + 修屋 + 采菜”；每次建设的材料不重复扣减。即使玩家不操作，自治也必须能摆脱常见的早期资源瓶颈。

### 5.4 建筑目录与解锁不是科技树

| 建筑/设施 | 真实建设原因 | 依赖 | 建成后的生活改变 |
| --- | --- | --- | --- |
| 营火和临时遮棚 | 防寒、避雨、睡觉 | 空地、枯枝、简单工具 | 居民晚间有归处；可继续修复 |
| 茅屋、简易储物棚 | 持续住人、物资怕雨 | 木料、劳力、安全地块 | 住房容量与保鲜能力改善 |
| 菜畦、晾晒台 | 食物不稳、采集距离过长 | 阳光、适宜土、种子/劳力 | 稳定食物、产生农业作业 |
| 土径、木桥／渡口 | 反复通勤、需要过河 | 通路、需求、施工材料 | 更快通行，开放另一片可用地 |
| 茶棚 | 行人停留/社交和招待需求 | 路口、能供热水、少量食物余量 | 访客能留下来，产生工作与消息 |
| 酒肆 | 访客逐渐稳定，茶棚容量不足 | 茶棚使用率、粮食/人手/地块 | 陆娘有新职业，江湖故事可触发 |
| 练武坪、工坊、商埠 | 有训练者/工匠/交易对象与地点 | 有关居民、场地、通行条件 | 出现新的角色行为和有形的生活中心 |

**同一类用途允许不同物理结果：** 食物问题可以先促成菜畦，也可能因为河岸与渔夫促成鱼棚；挡风处可以建棚，也可能先维修已有屋子。绝不做固定的“第 3 日升级茶棚，到了第 12 日解锁酒肆”。

## 6. 空间规划：从零开始消灭“贴模型与穿模”

Sprint 7 已有 `villagePlanning.ts` 的 OBB/SAT 占地、屋檐保护区、河岸/道路/崖边、重要松竹树木防护与稳定 seed，v0.4 应将其提升为**所有建筑都必须遵守的建造入口**。

### 6.1 完整的建设申请状态机

`Need → Intent → CandidateSurvey → ReservedSite → GatherMaterials → Foundation → Frame → Complete → Occupied / InUse → Wear / Repair / Expand / Relocate / Remove`

- 需求触发的是**建造申请**，不是直接添加 Mesh。
- 预备选址时检查房屋的 **最大屋顶、门廊、台阶、工作活动半径**，不只检查墙体。
- 新工地要包含运输/脚手架临时占地；不能因仅检查最终完成态就堵路。
- 建筑朝向应参考道路和坡度，门口必须能抵达路网；渲染用实际模型包围盒复核占地，不能用缩小模型掩盖明显失衡。
- 规划器必须为 **天然水系/未来河岸坡度、树根/灌木、悬崖、旧宅、住宅通道、公共活动区** 留出一致的保护区。
- 如果地块不可用，先尝试替代的建材/户型、缩减建筑规划、邻近扩建或更远的合规地块；仍不可用才发布“土地不足”的失败结果，保持资源和数据完整。
- 提交/施工/竣工时重复校验，预留期内他人不能抢占同一地块；不能靠在 Three.js 里把穿模建筑往旁边平移补救。

### 6.2 道路不是装饰性 ribbon

首间茅屋选址后，营火到屋门产生 **步行连接请求**；村民反复行走可形成踏迹，满足公共需求才逐渐铺为土径/石径。新桥/渡口是跨河图边，必须计算真正的可达性。

- `PathGraph`：营地、房门、水源、资源站、桥/渡口、山口为节点，道路为边。
- 为 `BuildIntent` 同时提出候选道路连接；**建筑 + 接入道路必须整体可行** 才接受地块，不准造孤岛屋。
- 动态连通图维护步行宽度与桥面安全净空；路不能穿越旧房墙壁、深河或悬崖。
- 居民寻路应使用最新图，不沿 v0.3 的固定 `dailyRoutePoints()` 去幽灵酒馆。施工后至少一位村民要实际走进新建筑使用。
- 田间小径的出现源于脚步使用，石路源于劳动与物资；两者保留可识别的视觉差异。

### 6.3 地貌与有限扩张

P0 继续使用现有一座微缩山谷，并给地形标记：可建坡度、洪水保护带、可耕地、林地、山口、河道、施工难度。首版不引入无限大地图；“地块不足”可能构成真实发展约束。长期可选：整治斜坡、修桥拓展河对岸和迁址，而不是无条件加大岛屿面积。

### 6.4 用地与建筑 ID

新模式不得继承 `inn-001`、五间老房和训练坪的 **初始占用**。可以复用它们的建筑原型/美术工厂，但只有真正选址并施工后才注册建筑实例。每个对象保持永久 `BuildingId`、`ParcelId` 与 `causeEventId`，拆迁后也保留历史而不复用 ID。

## 7. 玩家参与：少量介入，但有实际后果

### 7.1 守谷人不是每日指令调度器

默认不干预时，村民能建出可住、可吃、可通行的小聚落；玩家不做任何选择不会永远卡在篝火旁。

每季最多提供少量**重要方向性建议**（不强制出现，建议 P0 每季 0–2 个）。示例：

- **山雨将至：** 优先修避雨棚 / 优先收集粮食 / 让村民自行商量。不同决策改变施工优先级、库存和后续屋顶状态。
- **第一位过路客：** 留宿营地 / 指引山路 / 静观变化。只有已有安全的住处、热食才可能长久留下。
- **河对岸有平地：** 先修桥 / 先研究渡河 / 优先经营现有农地。随后由真实通勤需求决定是否动工。
- **林地渐稀：** 开辟新取材区 / 减少木耗 / 用石料替换。影响森林外观、材料和成长速度。

玩家可以在**候选建造计划出现时**提出区域偏好（如近水、避风、沿山道）或给予一次优先照顾，但最终地块必须仍通过合法规划检查。P0 不要求把房子手动拖到任意坐标。守谷人不插手，也必须得到一个可观察、可解释的选择结果。

### 7.2 可解释反馈：不是满屏数值

小型 HUD 只展示“今日乡邻最关心什么”“正在做什么”“为什么暂时建不成”；点击居民/建筑看到一句因果解释，例如：

> “梁伯选了背风坡，隔着河太远，陆娘暂时只搭了近水的棚子。”

守望录记录：需求源头 → 村民提议 → 守谷人/自治决定 → 材料和施工 → 竣工与谁入住。相同事件不可在快进中重复写入。切换 `流年` 后可以回看关键工程节点，但不需要演出长篇旁白。

## 8. 江湖内容何时进入？——故事从生活里自然出现

目前 `world.ts` 在固定分钟触发旅人，`VILLAGERS` 也是预设居住/工作坐标；新模式绝不能直接调用这套“开局就有酒肆”的条件。

新模式建议的**条件化故事门槛**：

1. **阿青出现／成长：** 山谷有可供家庭居住的房屋、稳定食物、适合活动的公共空间；可由居民出生/迁入事件引入，但第一版先用“随家人到来”避免在小切片里实现完整生育年龄系统。
2. **练剑：** 阿青已在谷、遇到愿意教他的人，有安全训练空间。练武坪可先是空地而不是开局的建筑。
3. **访客停留：** 山道可达、村民愿招待，且有热食与遮蔽；没有茶棚或酒肆的时代可以发生“借营火歇脚”，不能播放“酒肆掌柜端酒”。
4. **沈问舟入谷：** 由旅客信息/道路和当地接待能力触发；从真正入谷那一刻开始计算阿青的江湖分支时钟。
5. **雨夜留客/修缮机缘：** 必须绑定实际存在、处于使用/磨损状态的建筑，不能引用不存在的 `inn-001`。

原有 `host / observe` 两条选择和传承结果可保留为**后期 storylet 模块**，但触发时机是世界条件满足 + 相对事件时间，非一开始就沿用原 v0.3 固定天数剧情。

## 9. 建议的数据模型（设计合同，非已实现代码）

推荐独立 `PioneerWorldState`，而非在 v3 `WorldState` 上简单把建筑数组清空。共享日期/天气/渲染资产，不共享强制初始居民/酒肆逻辑。

| 领域 | 权威实体及主要字段 | 必须满足的不变量 |
| --- | --- | --- |
| 时间 | `ClockState {minutes, seed}` | 同一个 `minutes` 派生日/季/年；单步/流年/离线一致 |
| 地貌 | `NaturalSite {id, kind, position, remaining, regeneration, seasonality}` | 采集有来源、能耗尽/恢复；位置可重建 |
| 居民 | `ResidentState {id, presence, homeBuildingId, jobId, needs, taskId, socialLinks}` | 访客 ≠ 常住人口；住户房屋真实存在或登记为营地 |
| 住户 | `HouseholdState {id, memberIds, foodDemand, housingDemand, inventoryAccess}` | 人数、住房容量、食物扣除一致 |
| 建筑 | `BuildingInstance {id, archetypeId, parcelId, phase, wear, ownerId, occupiedBy, causeId}` | 所有永久建筑都经过规划器，实例 ID 不重复 |
| 工地 | `BuildIntent {id, reason, priority, candidates, status, cost, labor, parcelId}` | 施工前后占地合法；物资不重扣；失败有原因 |
| 空间 | `ParcelRegistry + RoadGraph + TerrainConstraints` | 房屋/屋檐/坡岸/路/树防穿模，门口可达 |
| 人与物 | `Inventory {siteId, stock, capacity}`、`TaskAssignment` | 同一人同一时段只有一项生产性任务 |
| 记录 | `CausalEvent {id, atMinutes, sourceIds, choiceId, outcomeIds}` | 快进可重放且不重复；每栋新屋可追溯 |
| 玩家 | `GuardianPolicy {preferredDirection, pendingAdvice, histories}` | 不做选择可自治解决；玩家不能强制放置非法地块 |

**稳定性：** 世界种子不应把 `Date.now()` 当成模拟世界内随机源。可以提供“随机开谷”和“输入谷种”；生成时记录 seed，此后所有决定仅用 seed、世界时间和稳定 ID，确保测试与复现。角色/建筑 ID 应由独立序列或稳定生成器分配，不能由场景加载顺序决定。

**存档与恢复：** 事件按 ID 幂等；导入校验所有建筑、地块、居民引用和路网连通；坏档应安全拒绝并允许恢复，不覆盖另一个槽。离线推进沿用有上限的既有策略，首次 P0 上限建议保持 v0.3 当前行为，另评估后再扩展。

## 10. 技术实施路线：明确什么复用、什么重构

### 10.1 原有代码可直接复用或抽象

- `src/simulation/calendar.ts`、`weather.ts`：单一时钟、季节天气，少改动。
- `src/simulation/villagePlanning.ts` 与 `valleyGeography.ts`：SAT、河岸、道路、崖边、重要树木的保护规则；需要将“开局老房保留地块”参数化。
- `src/graphics/carvedTerrain.ts`、`riverArt.ts`：流域地形、河面、瀑流、可视景观；保留视觉和模拟来源的一致性。
- `src/graphics/villageBuildings.ts`、`plannedSettlement.ts`：低多边形建筑原型与阶段施工；需要让 `archetype` 与 `BuildingInstance` 的施工状态解耦。
- `src/graphics/heroClips.ts` 等：作为后续出场人物的原型。不是已完成专业蒙皮/绑定资产。
- `tests/simulation.test.mts`、`tests/browser-smoke.mjs` 和 CI：沿用但拆出 v4 模式情境。

### 10.2 需要新增的模块（建议文件名，实际可调整）

| 模块 | 责任 | 不负责 |
| --- | --- | --- |
| `simulation/pioneerWorld.ts` | 新档初始化、总时钟编排、事件结算、v4 持久化入口 | 直接创建 Mesh |
| `simulation/residentNeeds.ts` | 人/住户基础需求、每天优先级与满意度 | 持久化 UI |
| `simulation/resourceSites.ts` | 林地/河岸/耕地真实产出、消耗和季节恢复 | 无中生有的每日数值 |
| `simulation/workScheduler.ts` | 单人劳动时间与工作位置、材料运输 | 渲染动作伪造工作 |
| `simulation/construction.ts` | 需求到工单、材料库存、工序与延期原因 | 跳过合法选址 |
| `simulation/pathGraph.ts` | 真实道路节点边、可达性、建筑与道路联动 | 只画装饰地面 ribbon |
| `simulation/settlementPolicy.ts` | 自治优先级、守谷人干预和异常恢复 | 直接指定永久房屋坐标 |
| `graphics/pioneerVillage.ts` | 空地/营火/工地/建筑/道路的实例呈现与拆除 | 修改 `PioneerWorldState` |
| `ui/modeSelect`（或现有 UI 组合） | 新旧模式选择、存档与开荒引导 | 无条件触发故事 |

### 10.3 不许以“隐藏旧村 Mesh”作为架构

旧 `village.ts` 可以提供纯自然地形与自然物件构建函数；新 `pioneerVillage.ts` 应只渲染 `PioneerWorldState` 中的真实实体。没有 `BuildingInstance` 就没有对应屋顶，也没有“明明没有酒馆却在背后运行酒馆维修”的幽灵状态。

若为节省开发量临时使用旧代码创建自然地形，必须从源头禁止旧建筑、NPC 固定工位、固定成长分区初始化；**只在 UI 层隐藏不可作为 P0 验收通过**。

## 11. 美术与动画守则

**视觉主题：** 明亮、干净、可辨认的中式山野微缩世界；从荒地的自然曲线，逐渐长出人造道路与不规则屋群。初期留白必须多，不能复制 v0.3 已经密集的房屋群。

- 营地、屋舍、茶棚、酒肆要有**整体造型等级**：临时织物/木架 → 可挡雨屋面 → 轻木构民居 → 有公共生活的屋群，而非在旧盒子上增加屋顶配件。
- 同类型建筑允许户型/方向/屋面不同，但必须共享统一的尺度、檐口、材质和颜色系统。
- 施工动作要与进度一致：有人搬运时木料移动、架子逐渐成形；无人施工不能靠渲染帧假装正在盖房。
- 村民不仅换工作地点，至少能在营火前围坐、拿柴、采摘、真正使用新屋。角色模型品质长期目标仍是高质量完整网格、骨骼和 `AnimationClip`，不是前胸/背部几何叠片。
- 新区增长必须服从构图：主要水脉与桥清晰，屋群之间保留步道与公共空地；默认镜头及转角不得互相吞没轮廓。
- 四季天气要改变实际生产与场景细节，避免仅调色；如春季返青、秋季收获、冬季取暖与雪后修屋。
- 调用当前仓库 Three.js 相关技能：`threejs-game-director`、`threejs-gameplay-systems`、`threejs-aaa-graphics-builder`、`threejs-qa-release`；角色 clip 采用已验证的 `CloudAI-X/threejs-animation` 方法。**技能是技术规范，不是美术完成的凭据**。

## 12. 开发阶段与闸门

### Phase A — P0「荒谷的第一间棚子」：第一版可以亲眼玩到的切片

**范围：** 模式入口与独立存档、自然山谷、三名开荒居民、营火、木料/食物/劳力、临时遮棚需求、合法营地/棚子选址、可见施工、居民使用、守望录因果、无操作自治。

**必须做到：**
- [ ] 新开荒的永久建筑数严格为 0；不会加载隐藏酒馆/房屋/练武坪状态。
- [ ] 1× 观察 10–15 分钟有可见的第一处真实工事（正常条件下可竣工第一处遮蔽）。
- [ ] 同个 seed 同个初始条件、正常播放/流年快进输出一致的棚子地点、资源和事件。
- [ ] 雨天缺料不凭空盖房，居民改派到合适的收集工作。
- [ ] 旧谷双槽、江湖分支与原渲染继续可玩，新谷不会覆盖其存档。
- [ ] Chromium 桌面和 390px 手机视口实测，没有隐藏模型、穿模或 Canvas 空白。

### Phase B — P1「居民自己建起村子」：真正验证长期生长

**范围：** 家庭住房与食物需求、资源点与再生、动态道路/门口可达性、扩建/修缮/迁址、人口与居民身份、新建筑选址、有限的守谷人引导；再加入 2–3 种生产建筑。

**必须做到：**
- [ ] 至少 3 个同种子且不同守谷人引导的存档，长到第 3 年后**建筑位置、道路或主要公共设施有实质不同**，不仅贴图和装饰不同。
- [ ] 同一发展方向换 seed，产生另一套合法村落格局；仍满足河岸/路网/建筑/树木净空。
- [ ] 所有房屋均可追溯“谁需要、何时提出、材料来自哪、何时落成、谁入住”。
- [ ] 新增道路真正被居民使用；没有孤岛屋、堵死桥、无限建筑重叠。
- [ ] 材料不足与土地耗尽有合理停工、转型或居民自治解决路径。
- [ ] 同种子不同推进方式（1×、跨季、导入/恢复）得到相同建筑注册表、资源和记录。

### Phase C — P2「烟火招来江湖」：融合现有武侠内容

**范围：** 茶棚→酒肆条件化成长、交易与旅人到访、沈问舟/阿青关系前提、`host/observe` 原分支与可重演的机缘系统；建筑生命周期与岁月外观。

**必须做到：**
- [ ] 荒谷阶段绝不触发酒肆招待、旧酒肆修缮或练武坪教学。
- [ ] 前置条件满足后，旅客才在有现实设施的位置停留，既有阿青故事从实际相遇时计算。
- [ ] 守谷人参与/不参与的后果均改变实体世界，可在守望录追溯。
- [ ] **不成为商业重镇** 也有稳定可继续观察的田园路径，不以负面结算强迫玩家选择商路。

### Phase D — P3「美术品质、性能与长寿命」

专业完整角色/动画资产、建筑形体统一精修、四季地貌细化、移动端 GPU budget、旧屋迁址/拆除/荒废、二十年以上长时间稳定性。此阶段**不是 P0 开荒模式上线的阻碍**，但应明列质量债，不得称作已完成。

## 13. QA 矩阵：怎样证明“不是预先安排的表演”

### 13.1 模拟层

1. `createPioneerWorld()` 初始永久建筑与道路为 0，只有合法营火和三位常住居民；不存在任何酒馆预制 ID。
2. 相同 seed + 相同玩家决策 + 相同时间推进方式 = 同样建筑、位置、道路、资源、事件、角色工位。
3. 相同 seed + 改变发展建议 = 在资源/合法地块允许时产生差异；不能只改变最终标题。
4. 不同 seed 相同建议 = 至少在资源分布、候选地块或聚落几何中发生真实可解释的差异。
5. 压力场景：连续降雨、寒冬、木料紧缺、粮食不足、全岛安全地块用尽、道路被施工暂占。自治不可死循环，必须返回原因。
6. 流年跨 12/48 日边界、长期离线恢复、重复导入、坏档、安全上限和两模式槽位隔离。
7. 施工消耗和产出守恒；无重复扣料、没有人同时在两个地方上班、游客不能凭空变成常住人口。
8. 所有永久建筑的屋檐 OBB/实际 Box3、工地、道路和河床净空合法；拆迁不会让旧 ID 冒名复活。

### 13.2 真实浏览器与美术

**固定 seed、固定相机、固定时间/天气** 分别记录：荒谷初始、第一间棚子施工、首屋落成、第一条路、第一年、第三年。再比较三种干预及不干预的平行世界，不能只比较 DOM 文字或模拟 JSON。

- 镜头观察：第一幅一眼看出荒谷而非被透明隐藏的老村庄；第三年又应明显形成村庄。
- 动画：搬柴确实对应木材运输、施工确实对应工地状态；人物可走到真实门口而非酒肆门口统一重叠。
- 空间：屋顶不穿模、入口不悬空、道路不断头、河流不被地形遮住；在玩家旋转镜头下也成立。
- 世界状态：暂停后模拟不继续推进；流年只改变模拟时间，不因为 FPS 差异刷两次建筑。
- 手机：保留可观赏岛屿的屏幕空间，机缘和建设信息不挡住整个山谷。
- 性能：报告 `drawCalls / triangles / frame time` 和实际设备；初版不应高于当前 v0.3 起点过多，后期逐步接近仓库 Three.js 美术技能给出的预算。无真机数据不可称“低端安卓适配通过”。

### 13.3 反作弊式“不是预制开关”的验收

系统产出的每一栋永久建筑均应满足：

- 有时间与居民需求可回溯的 `BuildIntent`；
- 有通过空间检验的 `ParcelId` 和可到达门口；
- 真实木料/工时消耗与可见施工中间态；
- 没有人出手也可能建设，但不会必然在每个存档的同一天同一位置出现；
- 完工后至少一名居民真的在此生活/工作，原有需求随之变化；
- 将其从保存记录中删除后，渲染不会继续显示该屋（无幽灵模型）；
- 物资不足或地块冲突时，**必须不建或调整方案**，而非悄悄写死生成。

## 14. 决策记录与待验证假设

### 本版已决策
- **双模式并存**，而不是覆盖 v0.3 旧村庄。
- **开局三人、零永久建筑、一处临时营地**。
- **轻度模拟经营 + 守谷人方向干预**，不升级成微操城建或数值点击。
- **所有永久建筑由需求生成**，没有强制第 N 日刷房；
- **空间规则优先**，旧谷遗留固定保留地块不得占据新谷。
- **先 A→B→C**，江湖故事等待现实接待设施，而不是反过来优先写剧情。

### 必须通过实际可玩体验验证的假设
1. **节奏**：前 10–15 分钟能否看到够明显的“无→有”，而不是无聊地等木头攒满？
2. **自主性**：玩家是否清楚“是村民做成的”，而不是一排数字到点自动跳？
3. **参与感**：每季 0–2 次关键决定是否足够有意义？过多/过少都要根据体验调整。
4. **表现**：小村庄仅几座房屋时是否仍然令人愿意观察？别以“建得越多越好”作为唯一胜利。
5. **空间**：同一岛屿尺度能否容纳从营地到 6–10 户民居并留下可通行道路？若不行应支持迁址/拓边，而不是缩小建筑硬塞。
6. **迁入节奏**：人口如何进入已有三个居民的社会网络，才能避免“新屋只有名字没有住户”？
7. **时间感**：48 游戏日/年是否足以表现建造、季节与角色人生？需先用真实游戏验证，**不为本版随意改时间基准**。

## 15. 建议的第一开发任务（交给 Codex 可直接拆解）

1. 新建 v4 开荒数据模型和模式隔离存档；写出 **“零永久建筑”初始化** 和旧谷不回归的测试。
2. 将 `village.ts` 中 **自然环境** 与 **旧村建筑** 的构造解耦；新模式只渲染自然环境 + 营火 + 真实实例。
3. 最小 `ResidentNeeds / ResourceSite / WorkScheduler`：三人分工取水/取食/取材，无人重复同时劳动。
4. 第一张营地选址及第一张遮雨棚的 `BuildIntent` 规划与材料事务，复用 Sprint 7 SAT/河岸/悬崖规则。
5. `Foundation → Frame → Complete → InUse` 的真实 3D 演出，营地与棚子能够被居民真实使用。
6. 做一个很轻的开局 HUD 和守望录因果记录，不要求完整科技树或新经济面板。
7. 实际 Chromium 浏览器验收 10–15 分钟开荒观察、流年重放、旧谷旧档兼容和移动端；不合格则停留在独立 PR，修正后才上线。
8. Phase A 通过后，再实现路网、住户/人口、第二种建筑和守谷人优先级，推进 Phase B。
