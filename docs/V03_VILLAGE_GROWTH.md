# 守望谷 v0.3｜建筑生命周期与自主村庄生长

> 状态：设计规格，尚未实现。原则：**村民使用世界，世界便留下痕迹。** 不把“房屋 +1”当作生长的全部表达。
> 关联：`docs/V03_WORLD_FRAMEWORK.md` / `docs/V03_PLAYER_AGENCY.md` / `docs/V03_ART_DIRECTION.md`。

## 1. 现状基线

v0.2 的房屋和道路大多由 `src/graphics/village.ts` 固定摆放，故事结局只显隐「竹隐剑庐」或「行脚茶亭」，并在 `src/simulation/world.ts` 将 `houses` 计数 +1。**没有每栋楼的身份、居民使用率、磨损、翻修与增建**，因而可见变化更像“场景切换”。

v0.3 不做任意地块编辑器；先让固定区域中的若干建筑与空地拥有**状态驱动的演变**。

## 2. 核心数据模型（建议 API，尚未实现）

```ts
type BuildingType = 'tavern'|'home'|'herbalHut'|'teaStall'|'trainingYard'|'storehouse'|'dojo';
type BuildingPhase = 'planned'|'foundation'|'construction'|'occupied'|'repairing'|'expanding'|'vacant';
type BuildingCondition = 'new'|'livedIn'|'worn'|'dilapidated';
interface BuildingState {
  id:string; type:BuildingType; plotId:string;
  ownerId:number|null; occupantIds:number[];
  foundedYear:number; yearsOld:number; conditionScore:number; // 0..100
  phase:BuildingPhase; workProgress:number; // 0..1
  useScore:number; // 0..100
  upgradeLevel:0|1|2;
  props:string[]; // 来自生活行为的耐久可视证据
  lastRepairYear:number|null;
}
interface PlotState { id:string; area:'tavern'|'homes'|'practice'|'riverside'|'forestEdge'; occupiedBy:string|null; accessNodeId:string; }
```

模拟层保存语义状态；`graphics` 只根据 `BuildingState` 决定几何变体、施工阶段和材质细节。**绝不能把 Mesh 本身当作存档事实。**

## 3. 每栋楼的生命周期

| 状态 | 条件与居民行动 | 3D 可视反馈 |
|---|---|---|
| 待建 `planned` | 村民形成需求，选定合法地块 | 木牌、测量绳、备料 |
| 地基 `foundation` | 工匠和材料到位 | 夯土、地基、砖石堆 |
| 施工 `construction` | 工匠日常工作、缓慢推进 | 立柱→墙体→屋顶→门窗 |
| 落成 `occupied` | 实际居住/经营 | 屋内灯火、门口道具、通行 |
| 有生活痕迹 `livedIn` | 使用与季节自然积累 | 踩实的门前土路、木色渐暗、添置杂物 |
| 破旧 `worn` | 多年风雨且维护不足 | 局部瓦色变化、褪色、补丁，不瞬间坍塌 |
| 修葺 `repairing` | 村民决定筹料修补 | 脚手架、木料、锤击动作、修后新瓦 |
| 扩建 `expanding` | 人口或业务需要 | 厢房、围栏、棚架、院落扩大 |
| 空置 `vacant` | 居民迁出或主人离世 | 门窗紧闭、灯光减少、野草增长；可再利用 |

数值门槛先作为可调参数：`80–100 新/良好`、`55–79 有生活痕迹`、`30–54 旧`、`0–29 急需修缮`。磨损按季节和使用率缓慢累积；修缮恢复状态但保留房龄与历史，不要重置为“从未有人住过”。

## 4. 需求驱动，而非脚本解锁

一个建筑提议的来源至少包含**现实需求 + 具体角色行动 + 空间条件**。

- 酒馆连续多季繁忙 → 门前添长凳/马桩/灯笼 → 满足客流后考虑扩建客房。
- 药农持续劳动 → 药架、药篓、晒药布渐多 → 合适时扩成药舍。
- 多位少年长期习武 → 木人桩数量增加 → 剑架/练武坪扩建 → 满足师资后才有剑庐。
- 家庭增加或迁入 → 先寻找可入住空屋，再提出新建民居。
- 洪雨季后木桥受损 → 村民会修桥，玩家可帮忙备料或提供祝福。

**每项发展都要追踪因果源**：`causeEventIds`、`builtByIds`、`residentContributors`，在建筑详情和守望录里可读。没有足够条件便继续积累，不随机“空降”新楼。

## 5. 小地图空间规划与建造安全

目前最明显的构图问题是村落中心仍有空旷区域、房屋重复、道路和建筑缺乏“生活关联”。本轮先设置**少量精心设计的建筑地块（plot/sockets）**，而不是动态任意落点：

1. 酒肆绝对中心；房屋在主山道两侧形成疏密有致的院落。
2. 练武坪与酒肆保持可见联系；河与桥、山门形成明确的外部入口。
3. 每个 Plot 有明确包围盒、朝向、出入口坐标和可扩建范围。
4. 新建前检查：地形占用、通道净宽、桥头和河岸安全距离、相邻建筑遮挡、摄像机默认朝向可读性。
5. 只允许可到达的空地触发建设；道路优先连接“门口—常用地点—酒肆—山门”，先用导航图，再做交通热度塑形。
6. 空间不足时优先翻修/复用/扩建，不挤出建筑或让房屋在岛边悬空。

**产出**：`plots.ts`（数据表）、`buildingPlanner.ts`（纯决策）、`buildingRenderer.ts`（分阶段几何），旧版 `home()` / `tavern()` 逐步组件化，不一次全部推倒。

## 6. 发展不只意味着“更大”

用三条可见轴代替单一房屋计数：

- **烟火气**：灯火、散步、路边摊、酒馆桌椅、晾晒、柴堆。
- **岁月感**：墙面磨损、瓦片修补、树木长大、旧址纪念、道路踩实。
- **江湖气**：剑架、来客坐骑、旅人包裹、收徒练剑、牌匾名声。

山谷可以选择长期保持小而安宁，也可以成为闻名江湖的驿站。成长不应强制走向“同一座大城”。

## 7. 玩家介入与自治规则

玩家可以支持“修桥、援助修屋、留出练武坪、帮助酒馆开客房”等**方向性计划**，但施工由居民完成。未回应时 NPC 可以按自身条件做保守决策；不会因离线而让所有房屋永久失修。

典型循环：
`酒肆热闹 → 增加客流/交通热度 → 老板娘提出添座 → 玩家可扶持 → 木匠取材 → 添座与灯火可见 → 更多旅人停留`。

## 8. 验收标准

- 从初始山村出发，至少 **2 处建筑** 可在不触发剧情结局的情况下发生可见状态变化。
- 至少 **1 处** 经历“新建→施工→落成”；至少 **1 处** 可经历“变旧→修葺”，并保留房龄和历史。
- 两个不同玩家选择导致不同可视变化，且都能从守望录反查原因。
- 快进/离线/存档重进不重复施工、不产生两栋同 ID 房屋、不让建筑浮空或截断道路。
- 默认视角和移动视口中，新建/旧/修葺状态可以肉眼区分，不依赖只有文字提示。
- 旧版结局建筑可以转换为有稳定 `id` 的 `BuildingState`；v0.1/v0.2 存档不被覆盖。

## 9. 首个开发切片（P0）

以 **酒馆 + 一间民居 + 练武坪** 为代表对象，先实现：地块/建筑状态 → 状态渲染 → 修葺/添置 → 存档 → 自动化测试。通过后才扩展到全村和自适应布局。
