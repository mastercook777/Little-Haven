# 守望谷 · v0.5.6「村居百态」建筑变体与地形生态约束 · 设计 / 实施规格

> **状态：逐阶段实施中。** P0 河岸/植被规则 PR #25 已合入 main；P1 山居首批四形制 PR #26 已合入 main，并通过 129/129 项测试及桌面/手机 Chromium 完整验收。后续其他功能设施形制、P2/P3 尚未实施。 本文是 v0.5.5「四时有声」之后的实施合同，不代表建筑变体、植被纠错或新布局已经上线。范围仅涉及开荒（pioneer）模式；经典观察版 v0.3 必须保持原有村庄、树木和独立存档。
> **用户反馈（2026-11-09，约第 2–5 年成熟村庄截图）**：住宅屋顶、体块和立面过于同质；画面可见树木落在河面上。目标不是“多几种屋顶颜色”，而是让不同人家的房屋拥有可信剪影、建造逻辑和生活痕迹；让每个自然物件服从同一块地形。

## 0. 目标、不变量与优先级

1. **P0 先消除穿帮**：所有永久树、竹、树桩和林地再生木，树干基部不得位于实际水面、不可站立河坡、路面、已建屋舍、施工用地和岛屿外；固定历史树位与动态森林统一校验。
2. **P1 再让建筑“不同”**：同类屋舍以屋顶形态、主体体量、正立面和开敞/围合方式产生可辨剪影；组件配色、盆栽、灯笼只是第二层微差，不可顶替 archetype。
3. **P2 随村落组织生长**：住宅成组、工坊靠近生产、鱼棚接近合法河岸、茶棚可见道路；任何选址与朝向都必须保留真实路径、建造支付、工时、可点击实体和持久 ID。
4. **P3 生活化与长周期**：住房入住、修缮、扩建与季节变化在模型上留下可信痕迹；不伪造库存、劳动、迁居或历史。
5. **保持开荒契约**：新档三位创始人、一处营火、零永久房；不预摆经典版酒肆；旧 v4 两槽存档和经典 v3 独立；不改江湖定位或强加生产系统。

### 1.1 具体的“树在河里”证据

现有固定植物坐标里，按 `VALLEY_RIVER` **折线近似**计算到河中心线距离（单位：Three 世界单位）：

| 旧锚点 | 坐标 (x,z) | 近似距河中心线 | 现状判断 |
| --- | --- | ---: | --- |
| `pine-3` | (4.7, 10.2) | 1.279 | 位于水面半宽 1.38 内 |
| `pine-6` | (5.3, -8.3) | 0.476 | 明显落在水中，属严重穿帮 |
| `bamboo-5` | (5.3, 10.1) | 0.988 | 竹丛落在水域内 |

**重要**：这些是折线距离的静态诊断，不是运行时样条河水 Mesh 的精确测量。最终 P0 验收须以 `riverArt`/`carvedTerrain` **共享的真实曲线和渲染宽度**复核根部/冠幅，检查用户截图中的具体树号。不要把“移开其中一棵”当作彻底修复。当前 `validatePioneerParcel()` 的河距离阈值 `.72` 是**地块外缘到折线的距离**，并不能替代水面宽度/视觉树根碰撞校验。

## 2. P0 · 唯一自然地形占用源（必须优先于美术变体）

### 2.1 共用河道几何，不允许三套近似各走各路

- 建议新增 `src/simulation/creekCorridor.ts`（纯数值、无 Three 依赖），提供 `distanceToCreekSpline(x,z)`、`surfaceHalfWidthAt(u)`、`bankOuterWidthAt(u)`、`isSafeNaturalFootprint(x,z,radius,kind)`；现阶段水半宽 1.38，外缘/岸坡可参考 2.42，具体宽度由共享的视觉河道规格统一。
- 为避免重写曲线后仍然错位，优先把河道曲线采样或样条参数抽成**同时供模拟验证和图形绘制消费的同源数据**；不允许只在模拟里对原折线加大一个魔法常量。与原 `riverArt` 的 Catmull–Rom 采样逐段对照，误差须在明确的世界单位阈值内（建议 ≤0.05）。
- 一个自然对象按其**根部/整个可见足迹**验证，不是只检查中心：树根 + 树干投影半径、安全空隙，竹丛需要多茎外展；大冠层可适度探出岸坡，但树干根部不得悬空或浸水。固定松、阔叶、竹和动态松/树桩均走同一函数。
- 禁布层：水域与河坡核心区、岛界/峭壁、行人可通行道路与入口、现有已建地块/施工意向及安全净空、营火和村心活动圈、其他实体的根部/可见足迹。**河岸专用矮芦苇/草丛是另外的规则**，允许在合法岸带，不按大树方式一概排除。
- 大树禁止区建议以 `距离中心线 >= 河岸外缘 + 可见根部半径 + 安全量` 为起点，再在实际曲线、地形坡度、模型尺寸上校准；不得把 2.42、1.38、2.47 等来自不同模块的数字偷偷混用。

### 2.2 新开荒模式专用且与模拟同步的植被锚点

- 不要直接改变 `VALLEY_PINES` / `VALLEY_BAMBOO` 影响经典村庄。建立例如 `pioneerNaturalAnchors.ts` 的 **pioneer 专用锚点表/解析器**：稳定 ID、种类、尺度、原始点、合法落点、保护范围、用途标签；迁移上述三处非法树位，其他锚点不随便重排。
- `pioneerWorld.landscape()`、`pioneerGrowth.natural()`、`pioneerVillage.vegetation()`、`pioneerHeritageArt.makePioneerSeasonalGrove()`、`pioneerAtmospherePlacement.PIONEER_DECIDUOUS_TREES` 和森林生成**必须消费同一套最终锚点**。杜绝树消失后仍有看不见的受保护地块，也杜绝装饰树画在可合法盖房的地块。
- 迁移要按稳定 ID、种子和可用地依次尝试本地候选；失败时明确跳过并有诊断记录，不得退回非法水面。根部与树冠高度对齐 `terrainHeightAt`，林地树桩和落木同样安全。
- 不允许把已经修复的树、花瓣或积水硬编码到某座未来住宅附近，避免两年后建筑扩建压住“树的幽灵”。

### 2.3 旧档与路网迁移必须一次完成、永久稳定

- **不许加载已有村庄时随机移动历史建筑、人物、道路、资源点或设施 ID。** 新谷已有 v4 存档；如果迁移后的受保护树位与老档真实建筑或路网冲突，应在**单次受控迁移**时作合法回退/跳过，持久保存锚点解析结果（可扩展兼容字段及校验，必要时升级存档 schema）；不得每帧/每次成长重新采样导致树木瞬移。
- 旧档迁移后的下一次保存/导入/离线补算必须保持同一锚点与相同 A* 可达性；未来伐木、重植、季节变化、天气组件只引用该实体 ID。正式实施前设计好 `getPioneerNaturalAnchors(world)` 的持久数据来源，而不是从“当前其他建筑占了哪块地”动态推导。
- **资源林地仍是聚合库存**：美术树木数量可按真实 `site.stock` 变，但不得新增免费木材；旧的倒树/树桩事件只在真伐木时出现。

### 2.4 自动审计接口（先定义再改造）

建议纯函数 `auditNaturalScene(world)` 返回 `{kind, anchorId, x, z, severity, reason, waterClearance, roadClearance, buildingClearance, islandClearance}`；首轮必须让上述 3 个非法固定锚点产生错误，修复后新档与迁移旧档均为 0 个严重项。碰撞失败要可回溯 ID/规则，不能用“无错误截图”代替真实水域检测。

## 3. P1 · 建筑 archetype，先换剪影，再谈装饰

### 3.1 三层生成结构与规则

1. **用途层** `PioneerBuildKind`：维持当前 shelter/garden/cottage/wood-yard/fish-hut/granary/tea-stop 的真实成本、岗位、容量与生产状态。
2. **形制层** `ArchetypeId`：外观轮廓、屋脊走向、墙体围合、檐廊和体块比。这一层的变化必须在默认正交相机和近景下都可辨认。
3. **细节层** `VariationSeed`：纸窗分格、门扇、栏杆、瓦色、陶罐/柴架、磨损、家户物件。变化不允许遮挡门或改变公共设施可用容量。

建议最少的可交付形制如下；**其中 C1–C4 已制作独立真实体块，其余编号仍属草案**：

| 建筑用途 | V1 目标形制（同用途不同剪影） | 关键视觉区分 | 不变的真实约束 |
| --- | --- | --- | --- |
| 山居 cottage | **C1 山墙小屋、C2 低檐阔屋、C3 前凹短廊屋、C4 偏檐侧作屋** | 屋高/屋脊、屋墙开合、前廊凹入、左右不对称；不要只换青/褐瓦 | 同一种 housing capacity；木阁须与每种屋顶匹配，不许凭空多一床 |
| 木作棚 wood-yard | **W1 敞梁作坊、W2 半围合晒木棚、W3 锯台木料侧棚** | 透空度、围护侧数、主梁/储木布局 | 锯台只有真实工艺投入后显示，工时与库存不变 |
| 渔棚 fish-hut | **F1 临岸轻棚、F2 高桩晒网棚** | 桩架高度、网架与檐影比例 | 渔鱼库存/待运鱼篓、入口合法、河岸安全不变 |
| 粮仓 granary | **G1 架高单仓、G2 架高连廊仓** | 高脚/台阶/通风口和仓门朝向 | 仍是同一处真实粮仓、容量只按原规则加 18 |
| 茶棚 tea-stop | **T1 路亭、T2 半敞篷茶寮** | 围护侧、旗牌、长凳/待客檐下空间 | 沿真实村路开放，访客需有人接待并支付材料 |
| 菜圃 garden | **P1 平畦、P2 半围合畦** | 畦向/篱笆/工具节点 | 土地库存、试种牌、可采数和种子命运链不变 |
| 避雨棚 shelter | **S1 原避雨棚**，后续再扩展 | 保留开荒第一屋的形象稳定性 | 起始三人无永久屋，建设不预支结果 |

**第一轮展示目标**：当同一种子成熟村庄 ≥4 间山居时，至少 3 种明显不同的屋舍剪影；其余已出现且不止一座的同类建筑，邻近重样优先回避。不同形制须用**轮廓差异**证明，不可仅以材料 UUID、灯笼有无等“变体个数”冒充。

### 3.2 形制参数接口（拟新增，尚未实现）

```ts
type PioneerArchetypeSpec = {
  id: string; kind: PioneerBuildKind; version: number;
  localForward: "+Z"; // 当前 pioneerEntrance 的门正方向
  roofProfile: {halfWidth: number; halfDepth: number; eaveY: number; ridgeY: number};
  envelope: {halfWidth: number; halfDepth: number; frontProjection: number; sideProjection: number};
  facade: "gable" | "broad" | "recessed-porch" | "side-workbay" | "open";
  sockets: {door: [number,number,number]; roofDrips: Array<[number,number,number]>};
  weight: number; minStage?: number; detailSet: string;
};
```

- **形制先于选址**：确定形制的碰撞包围与入口 → 才向 `pioneerGrowth` 申请地块与 `validatePioneerParcel` / A* 校验 → 再支付木料/工时与施工。不能先造完房子再把附厢伸进邻居地块。
- **v1 安全做法**：先把 C1–C4 等控制在当前相应用途已保留的 parcel/clearance 范围内（如山居已规划宽 3.10、深 2.95，视觉屋体约 2.64×2.50）；廊、台阶、瓦檐、木阁、雪层及材质尺寸都受这个 envelope 限制。较大偏屋必须在未来选址时申请真正更大的地块，不得偷用现有净空。
- 所有变体保持 `+Z` 门口坐标约定；改变正面/门位必须同时更新 `pioneerEntrance()`、道路终点、A* 通行和居民脚下工作点。
- **来源稳定**：推荐 `hash(seed, buildingId, kind, archetypeVersion)` 产生候选；为减少同片区重样，仅在首次建成前据周边**已有**建筑计算确定性择优结果，立刻固定在建筑的持久状态（或有严格向后兼容的稳定解析方案）。不得因 `world.minutes`、render frame、读档或后续迁居重新摇出不同房屋。
- 已建 v4 旧房可以选择可追溯的旧样式映射（视觉兼容），或执行一次确定性迁移并固定结果；不准改变原房屋的 `id`, `parcel`, `occupants`, `loftAddedAt`, `materialsSpent`, `workHours`。
- `pioneerHeritageArt.ts` 和 `pioneerRoof.ts` 共用 roofProfile 的实际几何；v0.5.4 曲面瓦面、冬雪及 v0.5.5 `pioneerRoofDrips()` 必须同步从同一形制 spec 导出，不能再按 kind 写固定檐高，避免新变体屋檐滴水漂浮。

### 3.3 细节随机范围与语义

| 维度 | 合法选项 | 绝对禁止 |
| --- | --- | --- |
| 立面 | 门扇/纸窗格、侧墙透空比例、木梁接榫、木材浓淡 | 出口被挡、墙体悬浮/穿透、床位随窗数变动 |
| 屋顶 | 屋脊走向、起翘强弱、翘檐、瓦列疏密、材质老化 | 同一屋顶叠两层、雪面/滴水不跟新曲面 |
| 屋外 | 陶坛、担架、木凳、门槛、晾网、柴架 | 凭空增加鱼/木/粮库存；附件跨 SAT 边界 |
| 使用痕迹 | 住满后灶烟/门前可见、粮仓满仓瓮、真实木阁修补 | 空屋假住人、未完成建筑提前有满仓物品 |
| 时间 | 建成时较新、condition 下降有旧化、修复后可见补缝 | 随帧随机刷旧色、未付修缮直接变新 |

## 4. P2 · 建筑“住成村”，而非程序摆放

现有 `pioneerGrowth.ts` 负责经济约束与候选地块，`pioneerPaths.ts` 有真实 A* 路网；**新选址偏好只做合法候选的排序，不能绕过 SAT/可达性和资源约束**。

| 用途 | 合法候选的软性择优 | 必须保留的硬约束 |
| --- | --- | --- |
| 住宅 | 靠可走乡路、与已有住户形成 2–3 户小邻里、门朝路而非统一朝屏幕 | 足够完整屋檐/门口净空，有真实可达的居民入口 |
| 木作棚 | 接近真实林地/木料运输方向，离民居适度远，留作业正面 | 不压伐木现场、清地缓冲和道路 |
| 渔棚 | 贴近安全岸带/鱼位，朝向可达路径；晒网架朝空旷处 | 不入水、不可跨河堤、不能截断运输鱼篓道路 |
| 粮仓 | 接近菜田/工作路，略独立，不堵多栋住宅的入口 | 容量、施工材料与建屋净空不变 |
| 茶棚 | 靠真实通行路线节点、视线可见，留有待客空间 | 真实访客进出、接待工时和交易不变 |
| 菜圃 | 与生活圈可达、适宜地形，多块田可有不同朝向 | 地块合法、真实种粮库存/试种状态不变 |

- 建议评分构成：合法性先过滤 → `accessDistance + roleAdjacency + sunlight/riverExposure + clusterCoherence + varietyPenalty + seededTieBreaker`。每项公开可调权重、输出候选被拒绝的实际原因。
- 每种 `kind` 至少两套合法朝向候选，路口临近入口优先；不擅自改掉当前 0 / 90 度旋转限制，除非真实屋檐/SAT/道路都能验证新角度。
- 不追求棋盘式整齐，也不强制“住宅必须成排”。保留小巷、树荫、村心空地、河岸生产区域之间的呼吸感，必须看得见“谁为了什么需要而建了这栋”。
- 扩张优先使用真实清灌过的合法土地；不能为看起来丰富而在地图边缘再放假的附属建筑。

## 5. P3 · 河岸生态带与生活道具

- 按距真实河道的带状距离（数值需用真实样条验证）将装饰分为 **水面**（仅水流/涟漪）、**砾石与湿岸**（石、水草、低芦苇）、**稳定岸地**（小灌木、竹边缘）、**村居与林缘**（松树、季相阔叶）。大树根部必须在稳定岸地；水中草不得使用大松树模型。
- 石块、芦苇应依岸线法线/曲率摆放，尺寸受限，避免石头挡住真实桥口/通行；与 `riverArt.ts` 既有石块和水纹共享河岸采样，避免额外第二套河石重叠。
- 各建筑附近的生活道具由**现有可验证状态**决定：`occupants>0` 的住宅可出现用具，`condition` 与 `lastRepairAt` 决定修补痕迹，`loftAddedAt` 决定真实木阁，鱼篓由 `fishTransport.pending`，粮仓瓮由真实库存、锯台由 `craft.phase`。没有状态依据的道具只能是无功能的小装饰。
- 四季落叶/花瓣/树根雪跟随迁移后的锚点；雨水溅落继续避开水面和屋内，屋檐流痕从形制实际檐口导出。不要牺牲 v0.5.5 的天气完整性。

## 8. 可自动化的验收矩阵

### 8.1 纯数值 / 模拟

- **精确水域 / 自然物**：以上 `pine-3`、`pine-6`、`bamboo-5` 在基线断言应失败；修复后所有树、竹、树桩、灌木、保护区合法，匹配同一条真实样条河道；必须覆盖水半宽和河坡外缘，不只检查中心线；树根所处地面高度一致。
- **多种子稳定性**：建议 seed 42 / 20261103 / 20261104 / 1001 / 1002 等固定种子组合（最终至少 20 种子随机审计），在 0、1、3、5 年和季节跳转后 0 处非法自然物、无路径断裂；记录每个拒绝的候选 ID/原因。
- **旧档**：直接导入已有人口/道路/住宅/木阁/渔棚/茶棚的 v4 保存，核验固定锚点与选址冻结、根部安全、下一轮保存恢复后不跳位；两槽开荒、经典 v3 互不修改。
- **建造合同**：任意 archetype 的屋顶、檐线、台阶、附属物 Box3 经旋转后不超出对应 `VillageParcel` 预留与净空；前门有真实 A* 路；施工阶段无成屋屋顶，付费/工时/居民容量原样守恒；稀缺地块时返回合法失败而不是穿模造屋。
- **变体稳定**：相同 seed、建筑 ID、建造历史在 1×/12×/流年/离线/读档模式下最终 archetype 相同；新增修屋、入住、季节不会重抽形制。

### 8.2 Chromium 与人工截图审美

- 固定同 seed/日期/镜头的**基线截图与改后截图**：新档三人营火、首座施工、第一年小村、第三年过渡、第五年成熟；至少正前、背后、左右四个视角及近景。
- 用户截图构图作为视觉复现目标：河上树根必须消失；同屏住宅之间屋顶轮廓、体量、门廊有辨识差别；关注河岸石/竹与建筑檐线/田地/路径的几何穿插。
- 春、秋、冬、雨各审查一次：保护树与叶片/花瓣/雪位一致；不同屋形屋檐滴水与瓦顶雪贴合；人物检视/建筑 Raycaster 不被装饰占用。
- 桌面 1440×900 与手机 390×844 正交视角、点击/旋转/触控无错，原 v0.3 经典场景两结局回归；必须保留 `tests/pioneer-browser-smoke.mjs` 五年真实增长验证。
- **审美判定不能自动化伪造**：最后要实际人工比较材质、重复轮廓、岸边植被层次与四角穿模；技术 CI 通过不等于画面达到预期。

### 8.3 性能和交付

- v0.5.5 的实测成熟村庄基线：约 **1066 draw calls / 75,626 triangles / 269 geometries**（Chromium 软件 WebGL 快照，并非安卓硬件 FPS）；新增屋体细节前先梳理材质共享、`batchStaticSubtree` 的 dispose 边界以及相同静态部件的 InstancedMesh。
- 每 Phase 输出新开档/第五年 `renderer.info` 的 calls/triangles/geometries、静态/动态更新负荷、截图哈希及浏览器错误；若 draw calls 比该 Phase 前上升超过 **5%**，需主动说明原因并补做批绘/降级，不把 5% 误称成性能达标。
- 真实低端 Android FPS / 发热和触控需要单独实测。设计目标是最终降低成熟村 1000+ 次 draw calls 的负担，但**不得为了压性能把住宅再次变成同一种造型**。
- 验证命令：`npm run test:sim`、`npm run check`、`npm run build:pages`、`npm run test:browser`；必须使用真实 Chrome 截图与可追踪 CI/Pages 结果。Phase A–D 分别 PR，合并后才更新 README 为“已实现”。

## 9. 范围外 / 决策冻结

- 不改变经典 v0.3 的固定树、屋、存档或剧情；不对既有开荒村存档中的家庭、物资、时间、住宅 ID 重新洗牌。
- 不新增矿业、铁匠铺、寺院、酒肆或江湖门派作为“丰富度道具”；真实功能解锁仍走 v0.5 成长树与世界观契约。
- 不在此轮要求导入第三方 3D 模型或付费美术资产；先利用现有 `villageBuildings` 曲面屋顶、材质 Kit、程式化建筑结构来证明真实形制变化。
